# 아이폰 키보드와 고정 셸 — 실측 기록과 남은 물음

편집 화면에서 타이틀을 치고 요약으로 포커스를 옮기면 화면이 통째로 비었다. 그 증상은
고쳤지만, 남은 「한두 프레임 흔들림」을 없애려다 **다섯 가지 접근을 실측으로 지웠다.**
이 문서는 그 다섯을 다시 시도하지 않기 위한 기록이다.

> **지금 코드에 살아 있는 것은 두 조각뿐이다.** `layouts/editor.vue` 의
> `--vvh`(셸을 키보드 높이만큼 줄임)와 `scrollTo(0, 0)`(WebKit 이 민 것을 되돌림).
> 나머지는 전부 되돌렸고, 그 근거는 각 파일 주석과 커밋 메시지에 있다.

## 전제 — 이 앱의 셸 규약

`layouts/editor.vue` 의 셸은 뷰포트에 고정되고(`height: 100dvh; overflow: hidden`)
그 «안»의 한 칸만 굴러간다. 지도가 있는 화면에서 헤더와 지도가 밀려 올라가지 않게 하려는
규칙이고, 거기서는 여전히 옳다.

문제는 이 규약이 **아이폰 키보드가 전제하는 것과 정반대**라는 데 있다. 가상 키보드는
표준상 «레이아웃» 뷰포트를 건드리지 않으므로(MDN: "the virtual keyboard only resizes
the visual viewport") `100dvh` 는 키보드가 떠도 화면 전체 높이 그대로다. 그런데 편집
1단계는 내용이 뷰포트에 딱 맞아 **문서도 안쪽 스크롤러도 스크롤 여지가 0** 이었다
(390×844 실측: document 0px, `.settings` scrollHeight == clientHeight).

그 상태에서 캐럿을 키보드 위로 올리려면 WebKit 이 쓸 수 있는 스크롤 상자가 하나도 없다.
그래서 시각 뷰포트를 통째로 민다.

## 기기 실측 — 무엇이 실제로 움직이는가

폰(iPhone 15 Pro)에 진단을 심어 이벤트를 시간순으로 받았다. 고정 셸에서 포커스를 옮길 때:

```
   0 focusIN   vv=397+0     win=397  sy=0     sc=0/744/280  summary@268
  ~100ms       vv=397+-396  win=397  sy=-396  sc=0/744/280  summary@664   ← 밀림
  ~+17ms       vv=397+0     win=397  sy=0     sc=0/744/280  summary@268   ← 되돌림
```

읽어낸 사실 넷:

1. **움직이는 것은 문서가 아니라 시각 뷰포트다.** `visualViewport.offsetTop` 이
   −396(= 키보드 높이)이 되고, 안쪽 스크롤러는 내내 `scrollTop 0` 이다.
2. **되돌리는 것은 WebKit 이 아니라 우리다.** `scrollTo(0,0)` 을 걷어냈더니 로그가
   `sy=-396` 에서 «끝났다» — 밀린 채로 남아 화면이 비고 하단 CTA 가 사라졌다.
3. **이 기기에서는 `window.innerHeight` 가 키보드와 함께 줄어든다**(793 → 397).
   표준 동작과 다르다. 한때 `--kb = innerHeight - vv.height` 로 CTA 를 밀었는데 그 값이
   기기에서 «항상 0» 이었고, 그래서 CTA 가 엉뚱한 자리에 섰다.
4. 지연은 90~113ms, 복귀는 11~18ms 로 **편차가 거의 없다.** 경합이 아니라 결정적 동작이다.

## 지운 다섯

| # | 시도 | 실측 결과 |
|---|---|---|
| 1 | 포커스 시 스크롤 여지 선점(임시 `padding-bottom`) | 키보드가 «이미» 올라온 상태의 포커스 이동에서 스크롤러가 그 빈 여백 속으로 굴러들어가 폼이 사라졌다 돌아왔다 |
| 2 | 문서 스크롤 되돌리기를 rAF 없이 즉시 | 24ms 가 18ms 로 줄었을 뿐. 움직이는 게 문서가 아니라서다 |
| 3 | `html/body` 의 스크롤 여지 닫기 | 밀림 그대로. 같은 이유 |
| 4 | 시각 뷰포트 상쇄(`translateY(offsetTop)`) | JS 가 합성 프레임보다 늦어 **반대 방향 흔들림을 하나 더** 만들었다 (로그의 `@-128`) |
| 5 | 문서 스크롤 = A안 (아래 별도 절) | 밀림은 사라지지만 「자석」이 생겼다 |

1·4 는 «고치려다 새 증상을 만든» 경우다. 2·3 은 무해하지만 효과가 없었다.
3(`html, body { height: 100%; overflow: hidden }`)은 원래 쓰지 않던 여지를 명시적으로
닫는다는 뜻으로만 코드에 남겼다.

## A안 — 문서가 굴러가게 두기

같은 화면에서 두 구조를 번갈아 잰 A/B 가 **처음엔 A안을 확정해 주었다**:

```
고정 셸     focusIN sy=0  →  sy=-396 밀림  →  17ms 뒤 되돌림
문서 스크롤 focusIN sy=70 →  sy=153 «정상 스크롤»(캐럿이 올라온 만큼)
            밀림 없음. 되돌아오지도 않는다 — 그 자리가 맞는 자리라서다.
            키보드가 오르는 동안 뷰포트도 42→30→22→…→0 으로 부드럽게 수렴한다.
```

그래서 1단계(폼뿐)에 적용했다. 그런데 실제로 써 보니 **타이핑 중에 폼의 나머지를 볼 수
없었다.** 원인은 「스크롤이 막힘」이 아니라 **자석**이었다:

```
6409 vvSCROLL sy=244        ← 포커스가 없을 땐 244까지 자유롭게 간다 (막힌 게 아니다)
6952 focusIN  sy=132
7044 SCROLL   sy=68         ← 포커스만으로 캐럿 자리로 끌려감
8095 SCROLL   sy=60 → 33 → 12 → 0    ← 손으로 0까지 내려진다
8237 SCROLL   sy=5 → 12 → 32 → 63 → 68   ← 떼면 68로 되돌아온다
```

3단계에도 복제했다가 되돌렸다. 3단계는 포인트 목록 + 편집 블록이라 문서가 통째로
길어지고(셸 1162px) 본문 입력칸이 문서 깊숙이(y≈734) 앉는다. 자석 바닥이 정확히
`sy=369`(= 734 − 397 + 여유)였고 손으로 그 위로 밀면 매번 369 로 되돌아왔다.

## 남은 물음 — 이어서 할 자리

**껍데기 없는 실험 페이지(`/test-scroll?mode=flow`)에는 이 자석이 없었다.** 같은 조건에서
캐럿이 화면 밖(`summary@-27`)까지 나갔고 `sy` 가 175~356 을 자유롭게 오갔다.

폼만 있는 두 화면이 다르게 구른다면 차이가 반드시 있다. 후보를 셋 지웠지만 남았다:

| 지운 후보 | 방법 | 결과 |
|---|---|---|
| 조상 사슬 | 두 페이지의 `overflow` · `overscroll-behavior` · `touch-action` 을 끝까지 비교해 맞춤 | 자석 그대로 |
| 하단 CTA | 진단에 토글을 달아 `display:none` (여백은 유지) | 자석 그대로 |
| 문서 길이 | 861 vs 1358 | 설명 안 됨 |

**조상 사슬 비교는 그 자체로 성과였다.** 편집 화면의 `.settings` 가 `.scroll-y` 에서
물려받은 `overscroll-behavior-y: contain` 과 `touch-action: pan-y` 를 그대로 이고 있어,
`overflow` 만 열었을 때 손가락 제스처가 문서로 «이어지지» 못했다. 밀리긴 하는데 매번
제자리로 돌아오던 증상이 이것이었다. 칸을 열 때 되돌려야 하는 것이 셋이라는 것을
`base.css` 주석에 적어뒀다 — 하나라도 빠지면 **각각 다른 증상**으로 조용히 어긋난다.

다음에 이어서 한다면 **실험 페이지와 편집 화면을 한 요소씩 옮겨가며** 좁히는 것이
남은 길이다. 지금까지처럼 「그럴듯한 원인」을 짚어 고치는 방식은 이 건에서 다섯 번
빗나갔다.

## 코드에 남겨둔 것

되살릴 때 처음부터 다시 재지 않아도 되게, 껍데기는 그대로 두고 조건만 껐다.

| 파일 | 상태 |
|---|---|
| `app/composables/useDocScroll.ts` | 살아 있음. 근거 주석 포함 |
| `app/assets/css/base.css` 의 `html.doc-scroll` 블록 | 살아 있음 |
| `app/components/PostSettings.vue` 의 `html.doc-scroll .settings` | 살아 있음 |
| `app/pages/editor/[slug].vue` | `useDocScroll(computed(() => false))` — **꺼짐** |

진단 도구(화면 위 이벤트 표 · 수집 엔드포인트 · `/test-scroll` 실험대)는 `main` 에서
걷어내고 **`experiment/ios-keyboard-probe` 브랜치에 보관**했다. 이어서 할 때 그 브랜치를
main 에 리베이스하면 폰에서 바로 다시 잰다.

## 방법에 대해 — 왜 진단을 심었나

이 건은 **폰에서만** 재현된다. 데스크탑 브라우저에는 가상 키보드가 없어 창을 줄이는
흉내로는 잡히지 않고, 실제로 그 흉내 때문에 한 번 틀린 검증을 했다(창을 줄이면 레이아웃
뷰포트까지 줄어 하단 CTA 가 따라오는 «것처럼» 보였다. 기기에서는 안 따라온다).

추측으로 네 번 빗나간 뒤에야 진단을 심었고, 그 뒤로는 판정이 한 번에 났다. 진단이
로그를 **파일로 보내게** 한 것도 중요했다 — 스샷을 옮기는 수고가 없어야 사람이 여러 번
재 준다. 다만 진단 자체도 세 번 고쳤다: 판이 조작 버튼을 가렸고, 묶음 간격이 좁아
「이어진 한 동작」이 쪼개졌고, 상한이 낮아 앞부분이 잘렸다.
