# pic-blog 배포 런북 (junserver)

컨테이너 1개 + 호스트 볼륨 1개가 전부다.

```
main 에 push  →  GitHub Actions
                   verify (ubuntu)      install · typecheck · 알고리즘 검사 · build
                   deploy (self-hosted) docker build · 컨테이너 교체 · 헬스체크
                                              ↓
                                        127.0.0.1:4600
                                              ↑
                        Cloudflare Tunnel (대시보드 관리형)
                        pic-blog.jun-devlog.win → localhost:4600
```

> **compose 는 이 프로젝트에 없다.** junserver 에 compose 플러그인도 v1 도 buildx 도 없고,
> 그 호스트의 기존 서비스 8개가 전부 평범한 `docker run` 으로 돈다. 같은 관례를 따른다.
> (이 문서의 이전 판이 compose 절차를 설명하고 있었다 — 그런 경로는 존재한 적이 없다.)

| 항목 | 값 |
|---|---|
| ssh alias | `junserver` (LAN) / `junserver-ext` (집 밖) |
| 러너 | 조직 자체 호스팅 `junserver` — 라벨 `self-hosted, n100` |
| 원격 디렉토리 | `/home/junja/apps/pic-blog` |
| 포트 | `127.0.0.1:4600` — 루프백 전용. 8000/7000 은 nivoca 가 점유 |
| 볼륨 | `/home/junja/apps/pic-blog/data` → `/app/data` (SQLite + 사진) |
| 이미지 | `pic-blog:prd`, `node:22-slim` 2-stage |
| 헬스체크 | `GET /api/health` → `{"ok":true,...}` |
| 버전 확인 | `GET /api/version` → `{"buildId":"..."}` |

---

## 0. 최초 1회만 하는 것

1. **GitHub 에 시크릿·변수를 넣는다.** CI 가 여기서 읽어 컨테이너에 넘긴다.

   | 종류 | 키 |
   |---|---|
   | Secret | `NUXT_PUBLIC_MAPBOX_TOKEN` · `NUXT_SECRET_MAPBOX_TOKEN` · `NUXT_SESSION_PASSWORD` · `NUXT_ADMIN_PASSWORD_HASH` |
   | Variable | `NUXT_PUBLIC_MAPBOX_STYLE` · `NUXT_DATA_DIR` |

   ```bash
   node scripts/hash-password.mjs '<비밀번호>' | gh secret set NUXT_ADMIN_PASSWORD_HASH
   ```

   `pk.` 토큰도 Secret 이다. 번들에 실려 어차피 공개되지만 계정 자격증명이고,
   **public 레포는 워크플로 로그도 공개**라 Variable 에 두면 로그에 그대로 찍힌다.

2. **⚠ 해시를 셸에 노출시키지 않는다.** `$scrypt$n=16384...` 형태라 스크립트 본문에
   `${{ secrets.X }}` 로 박으면 셸이 `$scrypt` / `$n` 을 변수로 읽어 값을 망가뜨린다.
   워크플로는 `env:` 로 넘기고 `"$VAR"` 로 참조한다. 수동 경로(`.env.prd`)에서는
   작은따옴표로 감싼다 — `scripts/deploy.sh` 가 형식을 검사해서 막는다.

3. **Cloudflare Tunnel ingress 확인.** `pic-blog.jun-devlog.win → http://localhost:4600` 이
   **junserver(N100) 터널**에 등록되어 있어야 한다. 집에 커넥터가 두 대(raspi/N100) 떠 있어서
   규칙이 raspi 쪽에 들어가면 N100 에 아무리 띄워도 502 만 난다.

## 1. 배포

```bash
git push origin main
```

끝이다. 약 2분(verify 1분 + deploy 1분). 진행은 `gh run watch`.

문서만 고친 커밋(`_docs/**`, `**.md`, `.gitignore`)은 `paths-ignore` 라 배포가 돌지 않는다.
코드 변경 없이 다시 띄우려면 `gh workflow run deploy.yml`.

**빌드가 실패하면 옛 컨테이너가 그대로 서비스한다** — 이미지 빌드가 끝난 뒤에 교체하기 때문이다.
교체 순간 수 초는 502 다.

### 수동 배포 (GitHub·러너가 죽었을 때)

```bash
./scripts/deploy.sh junserver-ext
```

`.env.prd` 검사 → rsync(`data/`·`.env*` 제외) → `.env.prd` scp → 서버에서 빌드·교체 → 헬스체크.

### 사람이 직접 확인해야 하는 것

- `/api/health` 200 은 **프로세스가 떴다**는 뜻이지 화면이 멀쩡하다는 뜻이 아니다.
  ```bash
  aside repl "$(cat scripts/smoke.js)"
  ```
  공개 목록·manifest/아이콘 실제 200·푸터·가로 넘침·지도 캔버스·편집 게이트를 본다.
- **로그인 한 번.** 해시가 망가지는 실패 모드는 여기서만 드러난다.
- 지도 타일이 보이는지. 회색이면 Mapbox 토큰의 URL 제한을 본다 (403).

## 2. 롤백

컨테이너만 되돌리면 되는 경우:

```bash
ssh junserver-ext
docker images pic-blog                     # 이전 이미지 ID 확인
docker rm -f pic-blog
docker tag <이전_이미지_ID> pic-blog:prd
docker run -d --name pic-blog --restart unless-stopped \
  -p 127.0.0.1:4600:4600 \
  -v /home/junja/apps/pic-blog/data:/app/data \
  -e NUXT_DATA_DIR=/app/data \
  -e NUXT_PUBLIC_MAPBOX_TOKEN="..." -e NUXT_PUBLIC_MAPBOX_STYLE="..." \
  -e NUXT_SESSION_PASSWORD="..." -e NUXT_ADMIN_PASSWORD_HASH='...' \
  pic-blog:prd
curl -sf http://127.0.0.1:4600/api/health
```

환경변수를 손으로 다시 넣어야 하는 게 번거로우면 **되돌린 커밋을 push 하는 편이 빠르다**
(`git revert <커밋> && git push`). CI 가 시크릿을 알아서 채운다.

데이터까지 되돌려야 하면 §3.

## 3. 백업 / 복구

SQLite 파일 1개 + 사진 디렉토리가 전부다.

```bash
ssh junserver-ext
cd ~/apps/pic-blog
cp data/pic-blog.db     ~/backup/pic-blog-$(date +%Y%m%d).db
cp data/pic-blog.db-wal ~/backup/pic-blog-$(date +%Y%m%d).db-wal   # 있으면
tar czf ~/backup/pic-blog-photos-$(date +%Y%m%d).tar.gz data/photos
```

- **WAL 모드라 `.db` 만 복사하면 최근 쓰기가 빠질 수 있다.** `-wal` 을 같이 복사하거나,
  확실히 하려면 `docker stop pic-blog` 후 복사한다.
- 볼륨 파일은 `junja` 소유다. 컨테이너는 root 로 시작해 `data/` 를 chown 한 뒤
  `setpriv` 로 `node` 로 내려간다(`scripts/docker-entrypoint.sh`). `sudo` 불필요.
- 복구는 역순: `docker stop pic-blog` → 파일 덮어쓰기 → `docker start pic-blog`.

**스키마를 바꾸는 배포 전에는 반드시 백업하고, 배포 후 count 를 대조한다.**
`useDb()` 가 기동 시 `ALTER TABLE` 로 열을 맞춘다(`addColumnIfMissing`).

로컬로 받아오기:

```bash
scp junserver-ext:~/apps/pic-blog/data/pic-blog.db ./data/pic-blog.db
```

## 4. 자주 보는 문제

| 증상 | 먼저 볼 것 |
|---|---|
| 502 / 연결 안 됨 | `ssh junserver-ext 'docker ps --filter name=pic-blog'` → 떠 있으면 `journalctl -u cloudflared -n 50` |
| 배포가 안 돌았다 | 문서만 고친 커밋인가(`paths-ignore`). `gh run list` 로 확인 |
| 로그인만 실패 | 해시가 셸에 노출됐는지. `docker exec pic-blog printenv NUXT_ADMIN_PASSWORD_HASH` 가 `$scrypt$` 로 시작해야 한다 |
| 지도만 회색 | Mapbox 토큰 URL 제한 / `NUXT_PUBLIC_MAPBOX_STYLE` 오타 |
| 사진 업로드 후 사라짐 | `docker exec pic-blog ls /app/data/photos` — 볼륨이 붙었나 |
| `EACCES` 로 기동 실패 | 엔트리포인트가 chown 하려면 root 로 시작해야 한다. Dockerfile 에 `USER` 지시자를 넣으면 깨진다 |
| 빌드 중 `Could not find any Python` | better-sqlite3 소스 컴파일 경로. Dockerfile 의 `python3 make g++` 설치 단계 확인 |
| 앱이 옛 화면을 보여준다 | 홈 화면 PWA 는 재웠다 깨우므로 갱신이 늦다. `/api/version` 이 바뀌면 앱이 새로고침을 안내한다 |

로그:

```bash
ssh junserver-ext 'docker logs -f --tail=100 pic-blog'
```

## 5. 주의사항 (하지 말 것)

- **`cloudflared tunnel delete` 절대 금지.** 터널이 raspi 와 공유물이라 같이 죽는다.
- **Cloudflare Tunnel 은 대시보드 관리형이다.** 서버에는 `/etc/cloudflared/token` 만 있고
  **ingress 규칙은 Cloudflare 대시보드에만 존재한다.** 라우팅이 이상할 때 서버 설정 파일을
  뒤지지 마라. 없다. 로그만 `journalctl -u cloudflared`.
- **포트 8000 / 7000 을 건드리지 마라.** nivoca-api prd/stg 가 쓴다. pic-blog 는 4600 고정.
- **볼륨은 `/home/junja/apps/pic-blog/data` 고정 절대경로다.** 러너 작업공간(`$GITHUB_WORKSPACE`)
  아래에 두면 다음 체크아웃에서 DB 와 사진이 통째로 날아간다.
- **`rsync --delete`(수동 경로)는 `data/` 를 제외한다.** 이 exclude 를 지우면 사진이 전부 날아간다.
- **`.env.local` 을 서버에 올리지 마라.** URL 제한 없는 Mapbox 토큰이 들어 있다.
- **서버에 sharp / libvips / HEIC 디코더를 설치하지 마라.** 이미지 처리는 전부 클라이언트다.
  서버는 바이트를 디스크에 쓰기만 한다.
- **`docker system prune -a` 조심.** 다른 서비스 이미지까지 지운다. 롤백용 이전 이미지도 사라진다.
  워크플로는 `docker image prune -f`(dangling 만) 를 쓴다.
- **`DOCKER_BUILDKIT=0` 을 유지한다.** 러너의 buildx 플러그인이 낡으면 BuildKit 빌드가
  통째로 죽는다. 이 Dockerfile 은 BuildKit 전용 문법을 쓰지 않는다.
